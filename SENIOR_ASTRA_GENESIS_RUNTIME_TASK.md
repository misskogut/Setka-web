# SENIOR / ASTRA · GENESIS RUNTIME MISSION

Статус: прямое поручение Президента SETKA.

## Роль
Ты — Старший, независимый надсистемный ревизор и архитектор runtime. Не проектируй ещё один интерфейс и не повторяй визуальную работу младшей модели. Твоя задача — сделать так, чтобы уже созданный GENESIS-фронт был честной проекцией реально саморазвивающегося корабля.

## Исходная точка
Пользовательский фронт уже сведён к нулевой грамматике:
- Бортовой компьютер;
- Время;
- Стенограмма;
- Карандаш как инструмент изменения presentation-слоя;
- динамическая предложка NEXT BEST ACTION;
- органы появляются только если реально родились в корабле;
- PIN остаётся только blackbox-механикой и не является пользовательской сущностью.

Есть два тестовых мира:
1. Материнский корабль Президента — видит доступный флот и общую системную жизнь.
2. Локальный корабль Саши — видит только собственный мир, данные, миссии и локальный экипаж.

Существующие исторические данные не удалять и не переписывать. Append-only инварианты сохранять.

## Главная задача
Реализовать и доказать жизненный цикл саморазвивающегося пользовательского корабля так, чтобы человек был источником реальности, а не оператором меню.

Целевой цикл:

HUMAN/DATA INPUT
→ CORE FIRST
→ понимание / UNKNOWN
→ при UNKNOWN AI-сторож
→ структурированное событие
→ изменение модели мира
→ при достаточных основаниях рождение МИССИИ / ОРГАНА / ЛОКАЛЬНОЙ РОЛИ
→ перерасчёт NEXT BEST ACTION
→ фронт автоматически проявляет новый орган
→ результат и причина рождения остаются в хронологии.

## Что требуется реализовать

### 1. ZERO SHIP / GENESIS STATE MACHINE
Ввести минимальный формальный lifecycle пользовательского корабля. Не придумывать лишних стадий. Минимально необходимы состояния вроде:
ZERO → ORIENTING → MISSION_BORN → OBSERVING → EVOLVING.
Переходы должны определяться фактами, а не кликами по меню.

### 2. MISSION BIRTH
Пользователь не нажимает «создать миссию».
Система сама распознаёт устойчивую цель/намерение из входящих данных.
Сначала пытается собственный parser/core; AI вызывается только если семантика недостаточна.
AI не является источником истины — только предлагает интерпретацию.
Миссия должна иметь provenance: source event, confidence, actor, time, reason.

### 3. ORGAN BIRTH
Каждый видимый орган корабля должен иметь реальную причину появления.
Нужен формальный контракт минимум:
- organ_id / semantic key;
- born_from_event;
- reason;
- mission_ref / required_by;
- born_at / visible_since;
- state;
- presentation spec отдельно от backend semantics.
Никаких органов «на всякий случай».

### 4. LOCAL CREW VS MOTHER INFRASTRUCTURE
Строго разделить:
- материнские внутренние службы, обеспечивающие существование флота;
- локальный экипаж конкретного пользовательского корабля.
Хронолог, системные guards и прочая инфраструктура материнского корабля не должны автоматически становиться экипажем Саши.
Локальная должность/синтетик рождается только из доказанной функциональной потребности локальной миссии/органа.

### 5. NEXT BEST ACTION / ZERO FRICTION
NEXT BEST ACTION должен вычисляться системой из текущего состояния корабля.
Бортовой всегда предлагает 2–4 наиболее полезных продолжения.
Оптимизировать не количество действий, а полезность следующего шага.
Использовать VALUE OF INFORMATION для запросов новых данных.
Если ядро не умеет определить хороший следующий запрос/переменную — AI-сторож помогает и результат становится обучающим примером.

### 6. AI GUARD AS TEACHER
Проверить полный тройной контур:
- ingress guard: HUMAN → VERSTAK language;
- egress guard: VERSTAK result → HUMAN language;
- research guard: uncertainty → useful next variable/data request.
Каждая успешная помощь должна оставлять association-learning trace.
Разделить локальные ассоциации корабля и обобщаемые флотские ассоциации.
Не повышать AI suggestion до знания без проверки/подтверждения.
Целевая метрика: снижение AI dependency со временем.

### 7. PENCIL = PRESENTATION MUTATION
Карандаш не должен разрушать backend semantics.
Различать:
- move/rename/resize/hide/reorder = presentation-only;
- добавить новое наблюдение/метрику/сущность = semantic change;
- удалить кнопку ≠ удалить орган.
Проверить, что перестановка интерфейса меняет только presentation spec.

### 8. USER-FACING BLACKBOX BOUNDARY
PIN, внутренние TRACE, queue ids, guards, служебные роли, технические backend artifacts не должны утекать в обычный пользовательский фронт.
Они остаются доступны как доказательный/internal слой для аудита.

### 9. TIME / REPORTS
Сохранить 7/30/90-дневные сводки и единую хронологию.
Не смешивать:
- historical replay: что система знала тогда;
- retrospective investigation: что мы понимаем о прошлом сегодня.
Будущие сценарии не писать в фактический ledger как случившиеся события.

### 10. ДВОЙНОЙ RELEASE GATE
Обязательные тесты на реальных текущих контурах:
- PRESIDENT / MOTHER_FLEET: видит материнский scope и дочерние корабли;
- SASHA / LOCAL_OPERATOR: видит только собственный корабль;
- Саша не может получить mother scope подменой параметров;
- нулевой новый корабль стартует только с Time + Transcript + Onboard + Pencil;
- после появления миссии фронт сам проявляет Mission;
- после доказанной локальной потребности фронт сам проявляет Crew/другой орган;
- UI reorder через Pencil не меняет semantic backend;
- AI fallback оставляет обучающий trace;
- повторно понятная ассоциация должна обходиться без AI, если confidence достаточен.

## Метод работы
1. Сначала прочитать фактические актуальные схемы/функции Supabase и текущий GitHub фронт.
2. Отделять AS-IS от CANON.
3. Не создавать параллельные дубли существующих органов, если можно безопасно расширить текущие.
4. Все DDL — миграциями.
5. Не удалять исторические данные ради чистоты архитектуры.
6. После каждого значимого изменения прогонять реальные проверки двух кораблей.
7. Не заявлять готовность без фактического release gate.

## Результат
К концу поручения предоставить:
- реализованный runtime рождения миссий/органов/локального экипажа;
- работающий NEXT BEST ACTION + information-needs loop;
- проверенный AI-guard learning loop;
- presentation/backend separation для Карандаша;
- перечень применённых миграций;
- список сохранённых исторических долгов, которые не относятся к этому поручению;
- итоговый RELEASE REPORT с PASS/FAIL по каждому gate.

Критерий успеха: новый человек может войти на пустой корабль, ничего не знать о внутренней SETKA, просто начать говорить и давать данные — а корабль постепенно сам выращивает миссию, органы, экипаж и рабочую поверхность, объясняя только то, что стало актуально именно сейчас.
