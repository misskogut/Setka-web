# SETKA: контракт паттернов v2

**Общий обязательный продуктовый контракт:** `SETKA_APP_CANONICAL_CONTRACT.md` (в корне репозитория) и журнал неизменяемых решений `docs/SETKA_APP_RULES_LEDGER.md`. Новые паттерны проверяются на целостность данных, реальное состояние синхронизации, правдивость метрик и отсутствие регрессий. Любое уточнение пользователя меняет общую платформу и её автоматические тесты, а не требует ручного добавления кода в новые паттерны.

Актуальные интерфейсы: `standalone-v34.html` и **`standalone-research-admin-v1.html`**. Историческая `standalone-admin-v34.html` сохранена для совместимости.

## Источники истины

- `standalone-pattern-registry-v1.js`: постоянные ID, версии алгоритмов и схем, параметры, ограничения, исходные значения, возможности, миграционные псевдонимы, ключи и снимки.
- `standalone-pattern-renderers-v1.js`: существующие восемь алгоритмов Canvas. Фронт, исследовательская админка, заметки и Replay вызывают этот код.
- `standalone-pattern-plugins-v1.js`: загрузка дополнительных реализаций из `descriptor.module`; событие готовности обновляет интерфейсы. Ошибка загрузки сохраняет карточку и пользовательскую запись.
- `setka-pattern-manifest-v1.json`: **генерируемый** транспорт того же реестра для сервера; не редактируется вручную. Версия оболочки manifest остаётся 1 для совместимости; контракт конфигураций — 2.
- Серверный каталог хранит названия и их редакционные ревизии; `setka_pattern_defaults_v2` — подтверждённые стартовые настройки. Эти ревизии не являются версиями алгоритмов.

`registry.normalize` — единая граница числовых диапазонов и типов. `registry.validate` проверяет значения без незаметного принятия повреждённого снимка. Ноль и `false` сохраняются. Явный неизвестный ID не превращается в Tentacle. Старые записи без ID распознаются только по однозначным параметрам; неподдерживаемая запись остаётся доступной как недоступная визуализация.


### Согласованное обновление опубликованного паттерна: касание и втягивание

У опубликованного `branching-impulse` новая реакция на палец должна быть **проверенной в живом интерактивном превью до публикации**, затем обновляется существующий модуль, не добавляется второй ID. При касании тонкой ветви расширенный hit-test выбирает заметный родительский пучок (`node <= 3`), который втягивается к началу; удержание сохраняет сжатие, краткий тап видимо срабатывает, отпускание плавно возвращает исходную геометрию. Внешняя свободная область отдельно управляет вращением. Реакция использует исключительно детерминированные `config + frame`, без таймера внутри renderer и без незаписанного состояния; старые снимки v1 восстанавливаются и воспроизводят исходное изгибание, новые касания используют v2. Параметры интенсивности и скорости реакции регулируются существующими ползунками, без новых кнопок в геймплее. При обновлении версии статус `published`, история, order, NEW, preset и реальные наблюдения не обнуляются. Тестовые демонстрационные кнопки предпросмотра не должны попадать во фронт.


### Genuary 16×16: осевые свайпы в новой геометрии

Для нового `genuary-16x16` восемь слоёв линий формируются общим детерминированным Canvas-рендерером с реальным перспективным преобразованием XYZ (вращение каждого слоя вокруг Z и стопки вокруг X). Каждый свайп начинается в одной из четырёх неизменяемых зон: левый край по всей высоте (↑↓ плотность), правый край по всей высоте (↑↓ 3D-наклон), верхняя середина (←→ толщина), нижняя середина (←→ скручивание). Первое движение больше 10 пикселей фиксирует только горизонтальную или вертикальную ось; движение по чужой оси не должно менять параметры. В `controls` каждого жестового параметра объявлены `fingers:1`, реальная краткая подсказка и тот же ключ, которым управляет ползунок. У всех параметров — целочисленная озвучка процента без видимых дробей; внутренние значения сохраняют точность.

Платформа допускает максимум девять палитр, но оригинал имеет десять цветовых состояний. `tapColorCycle:false` отключает общий девятирежимный тройной тап исключительно у этого модуля; его собственный декларативный `bindInteraction` хранит счётчик кратких касаний и реализует цикл десяти состояний: монохром 0 + инверсия 1, затем восемь динамических цветов. Тройной тап срабатывает после отпускания, свайп не засчитывается как тап. Все фазы, скорость интерполяции, 3D-глубина и палитры воспроизводятся по `config + frame` в игре, исследовательском Replay и миниатюрах, без скрытой `random`-фазы или `millis`.

### HexWave: зоны свайпов с приоритетом и панорамирование двумя пальцами

Новый `hexwave` подключается **одним самостоятельным модулем** через manifest/registry, так что фронтенд, админка, миниатюры, заметки и Replay используют общий рендерер и declarative schema. Первое белое состояние включает только белые основные точки на чёрном; RGB-глич-ореол из согласованного оригинала является регулируемым вторичным эффектом (`capabilities.rgbGlitchOverlay`), а не подменой палитры. Generic autodiscovery тест допускает при этой декларации исключительно красный/зелёный/синий ореол и требует видимые белые главные точки. Палитр ровно пять, смена — три коротких касания при отпускании (собственный `bindInteraction`, `tapColorCycle:false`). 

`right >= 40%` по всей высоте всегда имеет приоритет и меняет амплитуду (0–50) вертикальным свайпом с запоминанием исходного значения; остальные зоны: `top <= 33%` ←→ диаметр, `bottom >= 67%` ←→ скорость, `left <= 33%` в центральной трети ↑↓ радиус ячейки. Каждое направление одновременно обозначено бейджем ползунка. Рендерер хранит фазу волны через `wavePhase+waveFrame`, сохраняет скорость без скачка фазы, панорамирование и контактную историю в `config+frame`. Для `fingers:2` общий хост передаёт движение центроида; при переходе на два пальца неполный однопальцевый тап отменяется и больше не изменяет палитру. 

## Подключение новых паттернов: автоматическое обнаружение

После настройки платформы новый паттерн — **ровно один файл** `standalone-pattern-<id>.js`, содержащий два компонента:

1. В начале файла блок `/* SETKA_PATTERN_DESCRIPTOR\n{ ... }\nEND_SETKA_PATTERN_DESCRIPTOR */` с `id`, `title`, `version`, **`introducedAt` (UTC ISO 8601 — момент первого публичного добавления)**, `schemaVersion`, `module`, `defaults`, `controls`, `colorModes` и при необходимости `schema`, `keyFields`, `capabilities`. `introducedAt` записывается в единственный файл нового модуля, после выпуска не изменяется и не управляется его названием или просмотром.
2. Исполняемый Canvas-рендерер, который связывает функцию через `window.SetkaPatternRegistryV1.bindRenderer(document.currentScript.dataset.patternId, renderer)`.

После добавления единственного файла:

- `scripts/build-pattern-manifest.mjs` сам находит все такие модули в корне, извлекает JSON **без выполнения непроверенного кода модуля**, валидирует контракт реестром, пересобира реестр для развёртывания и публикует согласованный `setka-pattern-manifest-v1.json`;
- фронт и настоящая исследовательская админка используют один и тот же реестр и Canvas-функцию; загрузчик подхватывает модуль из `descriptor.module`;
- библиотека, динамические превью, карточки, параметры/жесты, заметки и слепки, история, статистика, серверный каталог и Replay наследуются от платформы и не получают отдельных ID-списков;
- CI проверяет автоподключение новых неизвестных модулей, стабильность сборки, отклонение неправильных дескрипторов, сохранение и воспроизведение всех новых рендереров; `tests/setka-app-platform-guard.test.mjs` блокирует ручные ID-исключения в общих модулях фронта/исследовательской админки;
- CI страницы блокирует публикацию при ошибках регистрации.

**Запрещено** добавлять дескрипторы новых паттернов вручную в `builtins`, редактировать HTML фронта/админки, SQL-перечни ID или создавать персональную логику карточек, превью и сохранения. `builtins` — наследуемые системные паттерны. Новые алгоритмы сохраняются только в своих файлах. Для локального просмотра после добавления файла выполнить `node scripts/build-pattern-manifest.mjs`.

**Обязательное правило стартовой палитры:** каждый новый паттерн открывается белой графикой на чёрном фоне. В дескрипторе `palettes` задаются RGB-варианты; `defaults.colorModeIndex` обязан указывать на `[255,255,255]`. Загрузка модуля и серверный manifest используют ту же палитру; сборка и тесты отклоняют новый паттерн с цветным стартом. Порядок уже существующих цветов нельзя менять, чтобы не исказить сохранённые конфигурации.

Автоматическая регистрация **не означает**, что любое сырое p5.js-тело автоматически становится совместимым с Canvas-runtime. Исходный алгоритм один раз адаптируется в модуль с декларативными параметрами. После этого всю инфраструктурную интеграцию выполняет сборка SETKA. Изменение визуального закона требует новой версии алгоритма, а несовместимое изменение структуры параметров — новой версии схемы.

### Расширяемое управление новыми алгоритмами

`registry.bindInteraction(id, reducer)` — опциональный обработчик трансформации конфигурации модуля. Общий фронт передаёт в него события `gesture` (стартовая зона, число пальцев, движение **центра** двух пальцев, текущий кадр) и `patch` (изменение бегунков). Редьюсер возвращает новую сериализуемую конфигурацию, которую проверяет и нормализует тот же реестр. Модули без обработчика продолжают пользоваться типовыми жестами без изменений. Это единственная расширяемая точка, а не особый `if (patternId...)` в приложении.

Для камеры с сохраняемой начальной позицией фиксировать якорь (`anchorFrame`, `originX/Y/Z`, `rollOffset`) в конфигурации при изменении скорости/ориентации. Рендерер не хранит позицию между кадрами и может воспроизводить кадры до/после якоря: это гарантирует движение превью даже после позднего сохранения и отсутствие разрыва при самой смене настроек. Палитры индексируются стабильно: новый режим добавляется **после** существующих; первый запуск — белый на чёрном; максимальное число режимов — 9.

При интерфейсе пространственной навигации один палец, начавший жест **в центре**, вращает камеру по двум независимым осям (вправо — курс вправо, вверх — нос вверх). Два пальца делают **стрейф** по экранной плоскости камеры, вычисленный по дельте центра касаний; зум/настройки/курс не меняются. Верхний, нижний, левый и правый край образуют четыре изолированные начальные зоны настройки, которые не меняются при пересечении границ в процессе жеста. Оставшийся после многопальцевого жеста палец не запускает одиночное управление, пока все пальцы не отпущены. Это правило реализуется в общей диспетчеризации только для модулей с `bindInteraction`; прежние обработчики неизменны. Повороты сохраняют прежнюю мировую позицию, боковое смещение сохраняет прежнюю ориентацию, а режимы `gestureHints` добавляют в единую панель инструкций описание жестов, не создавая несуществующих числовых параметров.

### Обновление опубликованного алгоритма и сохранение прежних версий

При изменении визуальной геометрии / добавлении параметров повышается `version` и, если расширилась схема, `schemaVersion` существующего однофайлового дескриптора, при сохранении `id` и исходной `introducedAt`. Существующий статус `setka_pattern_publication`, порядок в библиотеке, история и оригинальные `patternId` не изменяются.

Для добавления числовых контролов модуль указывает `legacyVersions`; общий `registry.restore` разрешает отсутствующие **новые** поля в точных слепках старой версии и нормализует их через декларативные значения по умолчанию. Все **присутствующие** прежние значения валидируются; новая версия требует полный набор. Записанный оригинал и исторические версии не переписываются. Геймплей, миниатюры и исследовательский replay продолжают использовать один renderer и frame/config.

Для пространственного управления зона определяется точкой **начала жеста**; правая полоса регулирует depth камеры, центральная зона независимо управляет yaw/pitch. Все изменённые координаты сериализуются в snapshot; auto-spring — независимая настройка. Не подменять смещение камеры масштабированием изображения.

### Медленные перелёты, остановки и независимое движение элементов

Однофайловый паттерн может объявлять скорость, управляющую детерминированной
длительностью участков пути и паузами. Во время остановки центр объекта
не меняет координаты, но инерционная физика сегментов продолжает
покадрово работать. На 0,05× медузы должны медленно доплывать и
долго оставаться в точке, чтобы щупальца успели раскрыться радиально;
0,35× — согласованный старт, 2× — максимальная скорость.
Без самостоятельной кнопки добавления и без «тап = добавить»:
количество медуз 1–30 изменяет только штатный числовой бегунок.
Всюду один renderer (геймплей/превью/снимок/исследовательский replay)
и тот же сериализованный конфиг, без дублирования ID.
Изменённый алгоритм сохраняет первоначальную дату публикации и допускает
старые сохранения через `legacyVersions` без переписывания исходников.

### Поведение счётчиков по тапу

Для модулей с числовым «Тап»-параметром дескриптор может задать
`tapOverflow: "clamp"`, при котором максимум не переходит к минимуму.
Без этого свойства сохраняется исходный `"wrap"`.
Кнопка «Добавить», бегунок и тап изменяют единый сериализуемый
параметр в конфигурации и сохранениях.

## Отзыв алгоритма без потери пользовательской истории

Если владелец SETKA отменяет новый паттерн, из корня удаляется его однофайловый
модуль `standalone-pattern-<id>.js`. Следующая сборка **автоматически**
исключает алгоритм из активного реестра, генерируемого манифеста и связанных
потребителей — пользовательской библиотеки, превью и активных каталогов
исследовательской админки. Запрещено оставлять ручные `if (id === ...)`
в UI/SQL или принудительно подставлять стартовый «осьминог».

Важное разграничение: удаление **модуля из активной поставки** не означает
удаления исторических записей людей. Ранее созданные избранные, заметки,
реплеи и событийная история сохраняют прежние `patternId`, `config`,
`patternVersion` и время. При недоступном архивном рендерере **не показывать устаревшие
элементы в активных галереях** (включая избранное/сообщество), не стирать
данные и не объявлять личную историю пустой. При необходимости статус
архивной записи должен находиться только внутри исторического просмотра
или экспорта данных. Историю
источника можно восстановить через Git, но она больше не участвует в сборке.
Если позже потребуется воспроизводить старые слепки, архивный просмотр
необходимо спроектировать отдельно, не возвращая алгоритм в библиотеку.

**Решение 2026-10-22:** `orbital-threads` («Орбитальные нити») отозван
из активной SETKA, а эксперименты со шлейфом отменены.
PR на воспроизведение старого шлейфа закрыт, не подлежит публикации.
Повторно включать этот алгоритм без нового запроса владельца нельзя.

### Автоматическая проекция активного каталога

Фронт использует `SetkaPatternRegistryV1.activeItems(rows)`, сервер —
`onlyActivePatterns(rows, activePatternIds(manifest))`; обе функции читают
только опубликованную идентичность и ничего не удаляют из сырых рядов.
Проекция применяется к базовой библиотеке, активным избранным, сообществу,
публичным заметкам/сценариям, рекомендациям и публичной аналитике.
Админка строит селекторы паттернов только из канонического реестра, но
архивные исследовательские факты не обнуляет.

Отзыв не требует ручного указания ID во фронте, на сервере либо в SQL:
`standalone-pattern-<id>.js` удалён, сборка исключила его из
`setka-pattern-manifest-v1.json`, и все активные представления ссылаются
на новое множество. Серверный кэш обязан обновить множество целиком,
а не только дополнять его. Ошибка загрузки манифеста не является
разрешением восстановить устаревшую публичную выдачу из базы.

## Единая истина для сообщества

В публичной галерее «Сообщество» показываются **только подтверждённые
сохранения зарегистрированных аккаунтов** из
`prototype_v41_config_metrics_current` (основана на
`prototype_v41_account_favorites`). Каждая карточка — одна уникальная
сохранённая конфигурация, ♥ — `save_accounts`, то есть число уникальных
аккаунтов с сохранением этой конфигурации. Разные конфигурации одного
алгоритма остаются разными карточками.

Старая таблица `prototype_v35_favorites` содержала сохранения **устройств**.
Её записи и показатели `legacySaveCount` больше не подключаются ни к
основной публичной ленте, ни к сердечкам, ни к текущим рейтингам, даже если
один старый вариант отсутствует среди сохранений аккаунтов. Никакой
подстановки из устройств, фиктивных пользователей или нулевых сердечек.

Браузер дополнительно отбрасывает строки с `historical=true` и
подтверждённым количеством `saveCount <= 0`, чтобы запоздалый ответ
старого сервера не возвращал устаревшие карточки. Исторические строки
остаются нетронутыми для исследования/экспорта; личное «Сохранённые»
читается из своего аккаунтного архива, а не из общей публичной выдачи.
Если нет подтверждённых сохранений — галерея пуста, а ошибка сети
показывает действительный статус, не синтезирует результаты.

`tests/standalone-v34-community-aggregate.test.mjs` и
`tests/standalone-v34-integrity.test.mjs` проверяют разделение
аккаунта/устройства, порогов раскрытия и отсутствие устаревших ♥.

## Управляемая публикация

Автообнаружение даёт административную доступность; новый ID получает `testing`.
`published` разрешает активный фронт, `disabled` скрывает его. Единственный
источник — `setka_pattern_publication`; общий серверный `loadPublishedManifest`
и клиентский `registry.applyPublication` применяют эту политику. Историческая
схема/версия/конфигурация не изменяется. Админский `manage-catalog` требует
проверенный ключ и сохраняет видимость скрытых алгоритмов для исследования.
Тестовая область использует `mountPatternEditor(draftOnly:true)` и тот же
рендерер; не запускает участническую телеметрию и не сохраняет стартовые настройки.
Публичный каталог передаёт опубликованные дескрипторы: новый ID регистрируется и загружает модуль в уже открытом приложении без ручного обновления страницы. Изменение версии существующего алгоритма требует согласованного обновления приложения. Каталог обновляется опросом раз в 30 секунд, не realtime.

## Контракт сохранения

Новый снимок заметки имеет `version:3`, `schemaVersion:2`, `configSchemaVersion`, `patternId`, `patternVersion`, `registryRevision`, `capturedAt`, `frame`, `seed`, `configHash`, полный `config`. Снимок создаётся при открытии редактора заметки; последующие выборы и административные настройки его не меняют. Исходный текст редактора остаётся при неподтверждённой записи. Неизвестные версии не заменяются базовым паттерном.

Ранее сохранённые RGB v35/v1 и десятипараметрический DNA обрабатываются явно описанными адаптерами. Реальные сохранённые цвета DNA имеют приоритет. Исходные архивы не переписываются миграцией.

Параметры алгоритма не равны записи микрофонного аудио: поток звука не записывается. Исторические микрофонные деформации без измерений восстановить невозможно; Replay не должен выдавать их за зарегистрированное поведение.

## Аккаунт и синхронизация

`standalone-data-scope-v1.js` назначает странице неизменяемую область `guest` либо `tester:<ID>`. localStorage, IndexedDB, избранное и последние конфигурации используют ту же область. Перед сменой аккаунта завершается локальная запись, затем меняется токен и перезагружается интерфейс. Ответы старого токена не могут подтвердить или подменить новый архив.

Старая общая локальная история копируется один раз; оригинальные ключи сохраняются для отката. Неоднозначная гостевая история не присваивается автоматически вновь вошедшему аккаунту. Приватный серверный архив остаётся реальным источником межустройственного восстановления; localStorage обслуживает локальную работу и очередь повторной отправки.

Обновление названий и стартовых настроек: публичный `catalog`, опрос каждые 30 секунд и при возвращении на страницу. Ревизии защищают от старого ответа. Версии manifest сверяются с клиентом; при несовпадении в библиотеке появляется обновление с предварительным сохранением данных. Build SHA добавляется к ресурсам всех актуальных интерфейсов, включая импорты исследовательских модулей.

## Нагрузка и воспроизведение

Библиотека отрисовывает максимум восемь видимых превью за проход, до 30 кадров/с. Остальные пользовательские и исследовательские превью — максимум восемь, до 20 кадров/с. Скрытые страницы, невидимые карточки и отключённое движение не требуют непрерывной отрисовки. Отключённые DOM-узлы удаляются из планировщика. Фоновая загрузка одной коллекции не пересоздаёт остальные.

Исследовательский Replay остаётся воспроизведением записанных событий и состояний с реальными временными отметками и указанием неполноты. BPM показывается только при наличии реальных совместимых измерений. Отсутствие данных не превращается в искусственную запись.

## Безопасный откат

До публикации основная ветка: `450b6e85a578cd65b2c63764c5070b9b0d32d2ef`; исходная точка аудита: `7b8ab4d07e299f37271e9b8240c34c65c602d007`. Откат приложения выполняется отдельным revert-коммитом с повторным CI, без удаления пользовательских областей и архивов. Предыдущие серверные реализации доступны в исходной точке аудита; перед заменой сверять реально развёрнутую версию.

Миграция `supabase/migrations/20261020183932_pattern_defaults_v2.sql` аддитивная: отдельная таблица и RPC, RLS и доступ только сервисной роли. Откат интерфейса не требует удаления этой таблицы. Удалять данные ради отката нельзя.

## Редакционный порядок и первое открытие (2026-11-03)

`setka_pattern_order` хранит единственный порядок, ревизию и историю изменений.
Сервисный `setka_set_pattern_order` проверяет владельца и ожидаемую ревизию;
`manage-catalog` отдаёт все установленные ID, публичный `catalog` — только
опубликованные. `registry.applyOrder` отвергает старые ответы;
`orderedIds` дополняет новые неизвестные ID без изменения потребителей.
`libraryIds(seen)` поднимает непросмотренные по выпуску (новые первыми),
а просмотренные сортирует по редакционному порядку; пустой порядок означает
прежнюю хронологию выпуска. Renderer/manifest revision и `introducedAt` не меняются.

`setka:pattern-open` и `setka:pattern-preview-open` после успешного явного
открытия используют один `openedPatterns` в существующем частном архиве.
Пассивные превью не отправляют это событие. Карточка информации не создаёт
PatternExposure/измеряемую сессию. Проверки расширяют
`tests/pattern-publication.test.mjs`, `tests/pattern-publication-db.sql`,
`tests/pattern-publication-browser.mjs` и выполняются существующим CI.
Откат кода не требует удаления таблиц/истории; прежний клиент игнорирует order.

## Быстрое управление карточками (2026-11-04)
В списке паттернов каждая карточка содержит публикацию/выключение, позицию со стрелками и раскрываемый редактор стартовых параметров с живым превью. Отдельного списка названий и позиций сверху нет. Кнопка карточки открывает полную исследовательскую статистику. Используются прежние ревизионные API; оригиналы и метрики не меняются. Открытый inline-редактор защищён от автообновления страницы; черновик порядка сохраняется при обычном обновлении статистики.
### Правдивые подсказки в компактной панели (2026-11-04)

Восьмой необязательный элемент `controls` — `[label,key,min,max,step,gesture,fingers,explanation]`, краткое текстовое объяснение действия регулятора. Общий реестр валидирует длину/тип, а компактная панель `standalone-pattern-key-v1.js` сохраняет только название и бегунок в строках. Дополнительный текст показывается исключительно по раскрытию общего `<details>` «Что делают бегунки?»; он также записывается в `aria-description` соответствующего input. Ни одна конкретная разновидность паттерна не кодируется в UI отдельным исключением.

`gestureHints` — только реальные жесты, а не описание смеси ползунков. Для модулей с собственным двойным касанием опциональный `tapColorCycle:false` предотвращает конфликт с обычным системным тройным тапом; без флага поведение прежнее. Движение пальцем не засчитывается как первая половина будущего двойного тапа. Доказательства: Node-тест будущего неизвестного модуля, опубликованный Radial Wave и реальное воспроизведение касаний в мобильном Chromium/WebKit; рендерер не создаёт параллельного состояния.

## Компактный визуальный порядок (2026-11-04, уточнение)
Над подробными карточками разрешена и требуется компактная сетка живых миниатюр по четыре в ряд. Это визуальный редактор того же общего порядка, а не отдельный список названий. Pointer drag одним пальцем перемещает паттерн в черновике; отмена жеста не меняет порядок. Сохранение использует прежний RPC, ожидаемую ревизию и read-back; до сохранения фронт не меняется. Стрелки клавиатуры и прежние карточные позиции сохраняют доступность. На подробной карточке видна кнопка переименования с подтверждённой записью и историей; статистика сохраняется. Личные New-группы продолжают иметь приоритет над общим порядком.

### Видимость мини-сетки порядка (2026-11-04)
В верхней мини-сетке порядка показываются только паттерны с подтверждённым `published`. `disabled`, `testing` и неподтверждённые скрыты только в мини-сетке; подробные карточки, настройки и статистика доступны для всех установленных модулей. Перетаскивание и клавиатура переставляют опубликованные элементы в их видимых местах, не теряя и не смещая скрытые позиции полного серверного порядка. После включения паттерн возвращается в сохранённую позицию. При отсутствии включённых показывается понятное пустое состояние. Проверки: `tests/pattern-publication.test.mjs`, `tests/pattern-publication-browser.mjs`.

### Полусферические спирали: адаптация исходной p5-геометрии (2026-11-04)

Декларативный однофайловый модуль `standalone-pattern-hemispheric-spirals.js` содержит оригинальную формулу двух зеркальных спиральных полусфер (радиус 420, спиральное вращение `r×0.02 + arm×0.8 + layer×1.1`, частоты 10 и 5,5 Гц, пространственные фазы `u×20` и `u×10`, не исчезающий коэффициент слоя `0.18 + 0.82×(1−k)`). Скорость имеет фазовый якорь, поэтому регулировка не создаёт скачка. Только девять палитр из 12 — авторский порядок выбранных режимов записан в исходнике, позиции не переназначаются. Шесть настроек, включая толщину из согласованного предпросмотра, объявлены в `controls`. Фронт автоматически получает `phase:start/move/end`, `pointerType`, мультитач-отмену первого касания и необязательный `wheel` через общий редьюсер; неконфигурируемые паттерны не перехватывают колесо браузера. Проверка изолированности зон, центра/вне центра, pinch, клавиш/мыши, сохранений и одинакового рендера — в `tests/standalone-hemispheric-spirals.test.mjs` и мобильных Chromium/WebKit smoke. Новые публикации по-прежнему требуют подтверждения редакционного `published` на сервере, отдельно от успешного деплоя кода.

### Interlaced Spirals — самоподобное переплетение (2026-11-04)

Новый самостоятельный декларативный файл standalone-pattern-interlaced-spirals.js содержит две зеркальные оригинальные p5-половины. Геометрия: radius=420u·breath, spiralTight=0.020+0.010·sin(t·0.25+L·0.6), layers scaled by 0.62^L; микроволны по u·(30+18L), переплетение u·(14+3arm), когерентные фазы 10/5.5 Гц. Реальный полный канвас в стартовой конфигурации имеет 1100 вершин в каждой линии, превью и густые конфигурации адаптируют только дискретизацию, а не уравнения. Все восемь независимых настроек объявлены в controls, включены честные пояснения в компактную панель, жесты инкапсулированы в bindInteraction. Пинч, свайпы, 3 касания, click/wheel проверяются браузерами Chromium/WebKit на настоящем canvas; регистрация и снимки — Node. Палитр 9, начало — белые линии на чёрном с исходной глубинной прозрачностью. Для добавления не меняем другие паттерны, общего хоста или исследовательскую админку; состояние публичного каталога подтверждается отдельно через серверный published/read-back.
