# SETKA APP — НЕИЗМЕНЯЕМЫЙ ПРОДУКТОВЫЙ И АРХИТЕКТУРНЫЙ КОНТРАКТ

Статус: **обязательные критерии проектирования и приёмки** пользовательского SETKA Web, платформы паттернов, аккаунтного архива, сообщества и `standalone-research-admin-v1.html`.

Зафиксировано: 2026-10-21. Этот контракт выражает целевое поведение, **не утверждает, что вся функциональность уже реализована**. Для действующего состояния всегда проверять код, работающие API, БД, CI и устройства. Не менять CANON, VERSTAK, Foundation/Diamond, прежнюю полную админку ради упрощения SETKA App.

## Постоянный протокол фиксации решений (SETKA APP)

**При любой следующей договорённости о поведении SETKA** исполнитель обязан не просто выполнить частную доработку, а:
1. формализовать правило в `docs/SETKA_APP_RULES_LEDGER.md` (APP-XXX), указать статус `реализовано / проверено / целевая функция`;
2. найти общий механизм реализации, убрать причину дублирования и не вставлять проверки ID новых алгоритмов в UI/админку;
3. дополнить декларативный контракт модуля/реестра и автоматический тест для **следующего ещё неизвестного паттерна**, включая ожидаемые сохранения, превью, порядок, настройки и исследовательский просмотр;
4. проверить стабильность всей затронутой системы на разных браузерах и после восстановления, а не только экран, который меняли;
5. сохранять оригинальные пользовательские записи, версионность, реальные метрики и безопасный откат;
6. публиковать только после проверок, затем сообщать отдельно о `CI PASS`, `деплой успешен` и `проверено на устройстве`.

**Согласованное пользователем правило обязательно для следующих версий без повторного напоминания.** Но текстовая фиксация сама по себе не доказывает, что требование уже автоматически реализовано: рядом всегда указывается исполняемый источник и доказательство. При конфликте с живым кодом — исправить код и тест, а не переписать продуктовый принцип задним числом.

Постоянный реестр решений: [docs/SETKA_APP_RULES_LEDGER.md](docs/SETKA_APP_RULES_LEDGER.md). Прочитать его до любых изменений SETKA App. Остальные ветки SETKA / VERSTAK / CANON / Foundation / Diamond не смешивать.

## 1. Главный закон

**Вся SETKA — одна система связанных сущностей и достоверных наблюдений. Изменение одного источника должно автоматически и согласованно отражаться во всех представлениях без ручных списков, локальных подмен, декоративных цифр и потери истории.**

Правильная цепочка: действие пользователя → проверенная запись → каноническая сущность/событие → версия/ревизия → доставка обновления → фронт/админка/аналитика → подтверждённое чтение и восстановление.

Каждый раздел обязуется явно различать: `loading`, `confirmed`, `pending local`, `stale`, `offline`, `unavailable`, `empty confirmed`. Неизвестное значение НЕ равно нулю, а ошибка доступа НЕ равна отсутствию данных. Запрет на фальшивый успех «сохранено», если запись не подтверждена соответствующим хранилищем.

## 2. Пользовательская поверхность и её смысл

- **Библиотека:** исходные алгоритмы, **Сообщество:** реальные сохранённые участниками варианты, **Сохранённые:** личные точные конфигурации. Все превью живые, соответствуют одной и той же геометрии/параметрам с геймплеем, показывают существующий статус, не замирают бесконечно. Исторические записи не удалять при временно недоступном рендерере.
- **Порядок паттернов:** непросмотренные паттерны находятся **вверху, самый новый первым**. После первого открытия метка `new` исчезает, а паттерн переходит в нижнюю группу просмотренных. **Вся группа просмотренных ВСЕГДА отсортирована по хронологии добавления в SETKA: старые выше, новые ниже.** Порядок открытия пользователем никак не меняет эту хронологию. Если все паттерны открыты, библиотека отображает ТОЧНЫЙ порядок создания алгоритмов — от первого до последнего. Для новых однофайловых модулей фактическая дата первого публичного добавления указывается один раз в `introducedAt` внутри дескриптора: сборщик сортирует по ней, а не по алфавиту имён файлов. Метка просмотра берётся только из истории пользователя, не создаёт независимого хранилища. Состояние переживает перезагрузку и восстановление архива. Квадратные превью центрированы; изменение порядка переиспользует Canvas.
- **Публичное сообщество — только зарегистрированные участники:** каталог опубликованных вариантов получает подтверждённые конфигурации исключительно из сохранений аккаунтов (`prototype_v41_account_favorites` и их серверной агрегированной проекции), а не из истории гостевых устройств. ♥ возле конфигурации — число уникальных зарегистрированных аккаунтов, сохранивших её. Публикация старых `prototype_v35_favorites` как действующих карточек запрещена. Тестовая/гостевая история сохраняется в архиве, но не создаёт публичные карточки, новые аккаунты или лайки. При устаревшей серверной выдаче фронт дополнительно отвергает `historical`-строки. Если подтверждённых аккаунтных сохранений нет, лента пуста с корректным статусом.
- **Геймплей:** чёрный фон, белая графика по умолчанию для нового паттерна, цветные варианты — только по выбору; жесты и бегунки управляют одними и теми же значениями; подсказка соответствует реально поддерживаемому жесту. Скрытие управления не меняет конфигурацию. Нижняя панель разделов не перекрывает геймплей.
- **Пять вкладок нижней панели:** Сегодня / Заметки / Пульс / Состояния / Я. Содержание разворачивается встроенной карточкой и сворачивается без потери контекста и черновиков. Не добавлять модальные окна вместо согласованных inline-потоков без функционального основания.
- **Сегодня:** запуск и завершение реальной сессии, запрос/оценка до/оценка после, история; измеряемая и свободная части разделены.
- **Заметки:** самостоятельный текст или неизменяемый слепок точного паттерна, версии, цвета, конфигурации и момента; никогда не заменять другим паттерном.
- **Пульс:** только реальные данные совместимого датчика с источником, временем, качеством и проверенной связью с интервалом просмотра. Никакой бутафории BPM.
- **Состояния:** отдельные отметки с сохранением временной истории, без пропажи после входа или синхронизации.
- **Я:** только личная статистика, аккаунт, сохранения, сессии, заметки, наблюдения. Публичная статистика — в общей карточке паттерна и исследовательской админке; не смешивать.

## 3. Обязательные канонические сущности

Читать `SETKA_DATA_MODEL_V1.md` и `docs/PATTERN_PLATFORM_V2.md`: Participant ≠ Device; Visit ≠ Session; Pattern ≠ PatternConfig; Favorite — отношение аккаунта к конкретной конфигурации; Note — отдельный текст с опциональным неизменяемым визуальным снимком; PatternExposure — **реальный видимый интервал**; Physiology — наблюдение с достоверным источником; RAW/Replay — свидетельство действий, а не альтернативный источник длительности просмотра.

Любое событие или объект передаёт устойчивый `id`, владельца/область доступа, `patternId` (если применимо), `patternVersion`, `configKey` либо полный снимок, время, ревизию/последовательность и статус подтверждения. Не создавать новую сущность только ради очередного экрана или графика.

Изменение стартовой настройки/публичного названия никогда не переписывает старый пользовательский слепок.

## 4. Новые паттерны — полностью системное подключение

После **однократной адаптации алгоритма** в файл `standalone-pattern-<id>.js` с декларативным дескриптором и renderer платформа обязана без ручного редактирования интерфейсов:

1. обнаружить и зарегистрировать модуль, проверить контракт, версии и обязательный монохромный старт;
2. создать элемент базовой библиотеки, живое превью, режим запуска, key-controls/жесты/палитры;
3. унаследовать избранное, заметки, слепки, сессии, состояния, usage, Replay, аналитику и общий каталог;
4. предоставить ту же реализацию рендера исследовательской админке;
5. автоматически выполнять регрессионные проверки на следующем неизвестном модуле, а не только на именованном Rain.

Запрет на второй список ID в UI, SQL или админке; запрет на «одноразовые» патчи `if(patternId === ...)` вне кода самого алгоритма, если функция общесистемная. Динамические превью и большой Canvas — **одна геометрия, разные бюджеты**.

## 4а. Отзыв паттерна — строго симметричная автосборка

Удаление одного файла `standalone-pattern-<id>.js` (или иное подтверждённое
исключение из канонического манифеста) означает **единую** операцию:
после успешной сборки и публикации ID больше нет среди активных алгоритмов,
поэтому все потребители автоматически пересчитывают *только представления*:
библиотека, переходы в геймплей, сохранённые активные конфигурации,
динамические превью, сообщество и публичные заметки, списки рекомендаций,
публичная аналитическая выдача и интерактивные селекторы исследовательской
админки. Удаляемые записи не должны появляться под повторяющимися карточками
«Слепок сохранён» и не должны попадать в активные счётчики.

Принцип симметрии: **один файл добавлен → активный каталог расширился;
один файл удалён → активный каталог сократился**. Запрещено искать паттерн
вручную и вычищать его по именованному ID из каждого потребителя.
Источником публикации служит один проверенный реестр/манифест; серверная
выдача активных вариантов фильтруется по этому же множеству, даже если
исторические строки сохраняются в базе.

**Удаление из интерфейса не равно стиранию личной истории.** Оригиналы
избранного, заметок, слепков, сессий и исследовательских событий
сохраняются под исходным `patternId` и версией. Отозванная конфигурация
не заменяется другим алгоритмом. Архивные записи не возвращаются
в активную галерею и не стираются при восстановлении аккаунта/перезагрузке.
Физическое уничтожение пользовательских данных — отдельная операция с
отдельным подтверждением, не часть жизненного цикла алгоритма.

Обязательный CI: создать неизвестный будущий модуль, проверить его
интеграцию, удалить только модуль, пересобрать, проверить отсутствие во
всех активных каталожных проекциях и неизменность старого частного архива,
а затем проверить повторное добавление и совместимое восстановление.
Проверка браузеров и реальная публикация сервера/Pages обязательны отдельно.

## 5. Синхронизация и поток актуальных данных: целевой контракт

**Текущее состояние не объявлять мгновенной синхронизацией:** каталог фронта сейчас опрашивает сервер примерно раз в 30 секунд и при возвращении на страницу; отдельные контуры синхронизации могут иметь собственные задержки.

Целевой канал:
- Действия/изменения идут через **каноническую транзакционную запись** с устойчивым `eventId`/idempotency key; только после её подтверждения событие доступно как подтверждённая истина.
- Фронт и админка подписываются на разрешённые изменения (поддерживаемый push/stream, выбор после аудита сервера). Получение — немедленная актуализация соответствующего read model и UI без полной перезагрузки/перерисовки всей библиотеки. Подписка не должна давать доступ к чужим приватным данным.
- Доставка может повторяться или приходить не по порядку: использовать version/sequence + idempotency и перезагрузку дельты. Восстановление соединения: cursor/watermark, `since`, reconcile, повторная подписка. **Один только WebSocket/SSE сам по себе не гарантирует консистентность.**
- Если push недоступен, использовать корректный fallback (периодическое обновление, при возвращении в приложение, при завершении сохранения). В UI честно показывать `обновляется`, `локально сохранено`, `облако подтверждено`, `нет связи`.
- Локальный черновик/очередь отправки остаются сохранными; конфликт владельцев и поздний ответ другого аккаунта отклоняются; запись нельзя считать подтверждённой до ответного read-back.
- Администраторские изменения имени/настроек и пользовательские сохранения проходят те же ревизии и проверку прав; интерфейс не пишет напрямую в привилегированные таблицы.
- Производительность измерять сквозными временными точками: `client-intent → request → commit → event → subscriber → UI paint` (p50/p95, раздельно frontend/admin), отдельно скорость рендеринга, память и лаги после возврата онлайн. Значения/целевые пороги определить по реальным замерам на iPhone и десктопе; не заявлять не измеренные SLA.

Нельзя скрывать серверный лаг перерисовкой UI, заменять неуспех статической заглушкой или синтетическими данными.

## 6. Никаких декоративных метрик

У каждой цифры/визуализации должен существовать проверяемый паспорт:

`metricId · human definition · canonical source · scope · time window · unit · deduplication · freshness · completeness · permissions`.

- ♥ явно означает: число **уникальных подтверждённых аккаунтов, сохранивших вариант** (когда показан этот счётчик). Не подменять количеством нажатий, просмотров или общими сохранениями алгоритма.
- «Популярное» — сортировка по реальным подтверждённым сохранениям, а не заполнитель из нулевых карточек. Ноль допустим только когда он действительно подтверждён; неизвестное показывать как отсутствие данных.
- Сессии, просмотры, длительность, количество участников — только канонические источники и соответствующая область выборки. Старые архивы/гости не удваивают живую статистику.
- График рисуется только из реального наблюдаемого ряда; gaps/unknown не соединять выдуманной линией. Демо/тестовую запись помечать явно и исключать из продакшен-аналитики.
- Утверждения «помогает», причинность и медицинский эффект не выводить из одних лайков, BPM или самооценок.

Любая кнопка, график, метка «LIVE», счётчик или статус обязаны соответствовать действительной функции.

## 7. Надёжность и удаление костылей

Постепенно заменить дублирующиеся состояния, локальные ad hoc кэши, дополнительные обёртки legacy-потоков и ручные списки общими контрактами. Сначала карта всех производителей/потребителей, затем безопасное удаление альтернативного источника — **не удалять legacy-данные, пока не доказано восстановление**.

Не заменять правильную исследовательскую админку урезанной версией; не трогать независимые линии продукта. Архитектурное упрощение измеряется: меньше независимых источников/патчей, равное или лучшее поведение, ноль потерь. Совместимость обеспечивается версионированными адаптерами и тестами, а не негласной конвертацией в starter-рисунок.

## 8. Обязательный сквозной тест для каждого изменения

Критически важная последовательность на двух клиентах и админке:
1. Первый вход/гость и подтверждённый аккаунт; сохранение/восстановление/смена аккаунта.
2. Базовый паттерн + новый автоматически обнаруженный паттерн; 1 и 2 пальца, тап, бегунки, ч/б старт и сохранённые цвета.
3. Живые превью при большом количестве карточек, прокрутке и длительной нагрузке; отсутствие пропаж и замираний.
4. Сохранение уникального слепка с параметрами, переход назад, перезагрузка, offline/online, восстановление на другом клиенте.
5. Заметка с конфигурацией + обычная заметка без паттерна, проверка точной реконструкции кадра.
6. Реальная сессия с несколькими PatternExposure, оценкой до/после, измерением при реальном датчике либо честным отсутствием датчика.
7. Общественная публикация/сохранение: положительные и нулевые значения, сортировка, счётчики, удаление собственного избранного без удаления общего объекта.
8. Изменение имени/разрешённого дефолта из админки → серверная ревизия → фронт → другой клиент → совпадающий read-back, без изменения старых слепков.
9. Доставка: порядок/дубликат события, разрыв и восстановление потока, устаревший ответ, конфликт ревизий, ошибка доступа, отсутствие сети.
10. Точная исследовательская карточка/Replay с тем же renderer и реальными событиями/метриками; отсутствие чужой и личной истории в публичных данных.

Автоматизировать unit + интеграционные + Playwright Chromium/WebKit; помечать реальный iPhone, BLE, микрофон и проверку приватного аккаунта как **not verified** до отдельных практических испытаний. Тестовый стенд никогда не пишет в реальную пользовательскую БД.

**Релиз заблокирован при:** потере данных, подмене неизвестного паттерна, фиктивном LIVE/BPM/♥, несовпадении фронта/сервера/админки, отсутствии защиты владельца, падении сквозного теста или недоступном обязательном модуле без честного статуса и пути восстановления.

## 9. Порядок доведения до готовности (без рискованного «переписать всё»)

**P0 — зафиксировать контрольную точку и реальность.** Бэкап, фактические функции Supabase, активные ревизии, карта сущностей/производителей/потребителей, инвентаризация всех текущих противоречий и способов восстановить исторические записи.

**P0 — устранить риски данных.** Подтверждение/восстановление сохранений, область аккаунта, ошибки записи, точная идентичность заметки/паттерна/версии, семантика сообщества и лайков.

**P1 — единый поток синхронизации.** Контракт событий, порядок/ревизии, клиентская подписка и серверные read models с проверенным fallback/reconcile; измерение сквозных задержек. Вводить постепенно по каждой сущности с параллельной проверкой, без дублирования истины.

**P1 — единый UI-рендеринг и избавление от точечных патчей.** Платформенный renderer, виртуализация/планировщик, унифицированная карта жестов и динамизируемые параметры; удаление старых альтернатив только после доказательства паритета.

**P1 — гейты CI и реальные устройства.** Дополнить тесты задержки, очередей/подписок, двух устройств, старых архивов, Safari/iPhone; фиксировать и сравнивать baseline. Запрещено закрывать задачу словом «готово» только по зелёному CI.

## 10. Definition of Done

Функция готова только тогда, когда одновременно:
- реализация не содержит дубликатов источников и специальных ручных интеграций, если задача общая;
- запись проходит frontend → backend → подтверждённое чтение → admin/другие клиенты и обратно;
- данные сохранены и остаются правильными после перезагрузки, смены контекста и обрыва сети;
- интерфейсы соответствуют тем же ID, алгоритмам, версиям и настройкам;
- отсутствуют декоративные метрики;
- существующие сценарии не регрессировали;
- есть проверяемые результаты тестов, протокол известной неполноты и способ безопасного отката.

**Условия из этого файла — требования к будущим изменениям, а не сертификат текущей готовности.**

## Уточнение владельца 2026-10-23: настоящие аккаунты тестовой группы

Разрешены десять полноценных аккаунтов test01–test10 в действующем проекте,
через обычные приглашения, активацию, пароль и сессии. Постоянный Tester ID
не переименовывается: имя и группа задаются серверной setka_account_cohorts.
Пока группа включена, подтверждённые события учитываются как обычные данные.
Последующее отключение отзывает входы и исключает группу из текущих метрик,
карточек сообщества, публичных заметок и сценариев. Сырые архивы сохраняются.
Это явное исключение к запрету тестовых записей в production выше, только
для помеченной группы владельца; разрушительные тесты общей инфраструктуры
и публикация экспериментальных алгоритмов в обычный каталог не разрешены.
Классификацию меняет только сервер с полномочиями администратора.
Доказательства: tests/account-cohorts-db.sql, tests/account-cohorts.test.mjs.
